# GitHub bridge and migration

## Outcome

Let repositories adopt the typed workflow and test model before trusting a new control plane.
Generate a minimal GitHub Actions workflow from `WorkflowPlanV1`, run existing bz tasks, and prove
semantic parity through dual execution.

## Bridge modes

### Action-body mode

The existing hand-written GitHub workflow retains triggers, jobs, matrices, permissions, and
runners. The bz Action replaces only command orchestration inside a job.

Use for immediate adoption and repositories with unsupported Actions features.

### Generated-workflow mode

`bz bridge generate` converts a workflow plan into a complete thin GitHub Actions workflow. GitHub
schedules jobs while bz owns the typed source and runner-local task behavior.

Use to validate distributed workflow semantics and eliminate hand-maintained YAML.

### Independent mode

The GitHub App and bz control plane schedule the same plan. No GitHub Actions workflow is invoked.

The repository can move between generated and independent modes without changing task methods.

## Generated file contract

Default paths:

```text
beelzebub.workflow.ts
.github/workflows/bz.generated.yml
```

Generated header:

```yaml
# Generated by bz 2.x. Do not edit.
# Source: beelzebub.workflow.ts
# Plan SHA-256: <semantic-plan-hash>
# Generator: <bz-version>
```

The generator:

- writes deterministic YAML;
- preserves no comments from a prior generated file;
- sorts jobs and maps deterministically where order is nonsemantic;
- includes source job IDs in names or metadata;
- pins the bz Action by immutable commit in strict mode;
- refuses to overwrite a file without its generated marker unless `--force` is supplied;
- produces no secret value or evaluated runtime-only expression.

`bz bridge check` regenerates in memory and fails with a concise diff when committed YAML is stale.

## Mapping WorkflowPlanV1 to GitHub Actions

### Triggers

Map supported push, pull request, merge group, schedule, and manual triggers directly. API-only
triggers receive a `workflow_dispatch` bridge only when explicitly requested.

Document semantic differences:

- GitHub path-filter evaluation and changed-file limits;
- cron scheduling delay;
- event payload differences for merge queues;
- skipped workflow versus skipped jobs;
- branch names versus full refs.

If bz cannot preserve a trigger's semantics, generation fails with an unsupported-feature
diagnostic rather than silently broadening execution.

### Jobs and matrices

Map:

- `needs`;
- matrix axes, include, exclude, max parallel, and fail-fast;
- runner requirement through a configured bridge mapping;
- timeouts;
- concurrency;
- environments;
- permissions;
- supported expressions;
- continue-on-error.

Runner mappings live in repository or account configuration:

```ts
bridge: {
  runners: [
    { when: linux({ cpu: 2, architecture: 'x64' }), runsOn: 'ubuntu-latest' },
    { when: linux({ cpu: 4, architecture: 'x64' }), runsOn: 'blacksmith-4vcpu-ubuntu-2404' }
  ]
}
```

Generation fails if no exact or policy-approved mapping exists.

### Job body

Each generated job normally contains:

1. `actions/checkout` pinned to an approved immutable reference.
2. Tool/runtime bootstrap required to run bz.
3. Dependency installation or a repository-defined bootstrap task.
4. The bz GitHub Action pinned to an approved immutable reference.
5. Optional bridge-only artifact or diagnostic steps where bz cannot yet provide them.

The long-term target is a self-contained bz Action runtime that does not require installing bz
before planning. Project dependencies may still be required by task files.

### Expressions

Only translate expression AST nodes with proven equivalent GitHub semantics. Unsupported nodes
must either:

- evaluate inside the bz job after GitHub schedules it, when doing so does not change dependency or
  permission behavior; or
- fail bridge generation with a diagnostic.

The generated workflow includes no user-authored raw `${{ ... }}` strings in strict mode.

## Existing GitHub Action hardening

### Bootstrap

- Bundle the runner entry point and compatible planner loader.
- Resolve the project's declared bz version for task execution.
- Verify supported version range and give upgrade guidance.
- Support npm, pnpm, yarn, and a custom bootstrap command through explicit configuration.
- Avoid executing a shell unless the repository requests shell semantics.

### Inputs

Retain current inputs and add versioned structured support for:

- plan path/hash;
- job ID and matrix values;
- event fixture location for bridge parity;
- expected task outputs;
- summary and annotation policy;
- debug bundle on failure.

### Outputs

Add:

- result and conclusion;
- task count;
- plan hash;
- structured job outputs;
- artifact/cache operation summary;
- diagnostic count;
- bz runtime version.

Outputs must observe GitHub size limits and fail explicitly on overflow.

## Marketplace action strategy

Full action emulation is not a bridge requirement. Migration classifies every `uses` step:

1. **Native bz replacement**: checkout, tool setup, cache, artifacts, Docker, cloud auth.
2. **Bridge-only supported action**: retained as a generated GitHub step.
3. **Command-convertible action**: replaced with a documented CLI or bz task module.
4. **Unsupported action**: requires a custom task or blocks independent cutover.

Maintain a compatibility catalog with:

- action and pinned version;
- inputs and outputs used;
- secret and permission requirements;
- replacement module or rationale;
- bridge support;
- independent-mode support;
- tested operating systems.

Do not claim support based only on action name; test exact behavior used by representative
repositories.

## Migration analyzer

Command:

```text
bz migrate github-actions .github/workflows/ci.yml
```

Analyzer output:

- triggers and filters;
- permissions at workflow and job levels;
- job graph and matrix;
- runner labels;
- environments and concurrency;
- `run` commands and shell dependencies;
- action inventory with immutable pin status;
- secrets, variables, outputs, artifacts, caches, and services;
- expression features;
- unsupported behavior and migration risk;
- proposed `defineWorkflow()` and `BzTasks` skeletons;
- estimated automatic/manual conversion percentage.

Generated code is a starting point and never committed automatically without an explicit flag.

## Migration workflow

### Step 1: inventory

1. Parse every active workflow file.
2. Identify trigger overlap and cross-workflow dependencies.
3. Record required branch checks and environment protections.
4. Inventory organization-level reusable workflows and actions.
5. Establish baseline run duration, queue time, flake rate, and failure categories.

Deliverable: migration report checked into `plans/ci-migration.md` or stored as a bz report.

### Step 2: extract runner-local behavior

1. Convert command steps into `BzTasks` methods.
2. Convert sequential command orchestration into `$pipeline()`.
3. Replace shell conditionals with typed task code.
4. Add injected command/runtime unit tests.
5. Keep scheduling YAML unchanged.

Gate: existing GitHub jobs invoke bz and produce equivalent outcomes.

### Step 3: define distributed workflow

1. Add `defineWorkflow()` jobs, dependencies, matrices, permissions, and runner requirements.
2. Validate and snapshot `WorkflowPlanV1`.
3. Generate bridge YAML.
4. Check generated YAML in CI.

Gate: generated topology matches the inventoried current workflow.

### Step 4: dual run

1. Keep the original workflow required.
2. Run generated workflow under a unique Check name.
3. Correlate runs by commit and event.
4. Compare planned jobs, command trace, outcomes, outputs, annotations, summary, and artifact hash.
5. Classify differences as expected, bridge limitation, or bug.

Gate: thirty consecutive days without unexplained differences.

### Step 5: generated bridge authority

1. Make generated Check required on a low-risk branch.
2. Retain manual original-workflow dispatch.
3. Observe another release cycle.
4. Remove duplicate original scheduling only after rollback is tested.

### Step 6: independent shadow

1. Install bz GitHub App.
2. Run independent bz Check as non-required.
3. Compare against generated GitHub bridge.
4. Validate GitHub Actions outage drills.

### Step 7: independent authority

1. Make bz Check required.
2. Retain bridge workflow as manually dispatchable fallback.
3. Document emergency activation and consistency implications.
4. Remove fallback only when organizational policy permits it.

## Parity record

For each correlated job, store or calculate:

```ts
interface ParityRecord {
  repositoryId: string;
  sourceSha: string;
  workflowPlanHash: string;
  logicalJobId: string;
  matrix: Record<string, unknown>;
  leftProvider: 'github-actions';
  rightProvider: 'bz';
  commandDigest: string;
  outcome: Comparison;
  conclusion: Comparison;
  outputDigest: Comparison;
  artifactDigests: Comparison[];
  annotations: Comparison;
  duration: DurationComparison;
  reviewedDifference?: DifferenceDisposition;
}
```

Command digest uses executable, argument vector, cwd, and a redacted allowlisted environment—not
raw secret-bearing process state.

## Implementation work packages

### BRIDGE-01: deterministic YAML emitter

- IR-to-Actions mapping.
- Generated header and plan hash.
- Stable formatting and check mode.
- Unsupported-feature diagnostics.

### BRIDGE-02: runner mapping policy

- Capability matcher.
- GitHub-hosted, Blacksmith, and custom-label configurations.
- Exact mismatch explanation.

### BRIDGE-03: action bootstrap hardening

- Self-contained entry point.
- Project-version resolution.
- package-manager adapters.
- output and diagnostics contract.

### BRIDGE-04: Actions parser and inventory

- Parse workflow syntax without evaluating unsafe expressions.
- Extract feature/action/secret/permission inventory.
- Produce risk report.

### BRIDGE-05: migration code generator

- Generate workflow and task skeletons.
- Preserve source references in TODO diagnostics.
- Never overwrite edited files without confirmation.

### BRIDGE-06: parity service and report

- Correlate runs.
- Compare safe semantic data.
- Render unexplained differences.
- Require explicit disposition.

## Tests

- Golden generated YAML for every supported IR feature.
- Parse generated YAML with GitHub-compatible schema validation.
- Execute representative generated workflows in a dedicated GitHub test repository.
- Test runner mappings with all supported resource classes.
- Test unsupported features fail closed.
- Test stale generated file detection.
- Test migration analyzer against anonymized real workflow fixtures.
- Test dual-run comparison with reordered logs and equivalent outcomes.
- Test fork PR permissions and secrets in bridge mode.

## Exit criteria

- Three repositories run task-body mode with meaningful workflow unit tests.
- Three repositories generate deterministic GitHub workflows from WorkflowPlanV1.
- The compatibility catalog covers every action used by those repositories.
- Dual-run comparison has no unexplained semantic difference for thirty days.
- A documented rollback returns a repository to its prior required GitHub workflow.
- No bridge limitation is misrepresented as independent-mode support.
